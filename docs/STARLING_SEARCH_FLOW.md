# Starling Search Flow

This document explains the current Starling search pipeline based on the actual implementation in `scripts/`, `tests/`, `src/`, and `include/`.

It covers:

- KNN search
- range search
- beam search
- page search
- in-memory navigation graph seeding
- cache-node loading
- SQ search
- major search parameters and their actual runtime meaning

## Overview

Starling search is driven by `scripts/run_benchmark.sh`, which dispatches into two binaries:

- `tests/search_disk_index` for KNN search
- `tests/range_search_disk_index` for range search

Both binaries build a `diskann::PQFlashIndex<T>` and then choose one of several runtime search paths:

- DiskANN-style cached beam search
- Starling page search
- Starling page search with SQ
- iterative KNN-to-range search
- custom page-search-based range search

## Search Initialization Flow

Both KNN and range search initialize the runtime in roughly the same order.

### 1. Parse CLI arguments

The CLI layer validates:

- data type
- metric
- `disk_file_path`
- `mem_index_path`
- `use_page_search`
- `use_ratio`
- `use_sq`
- range-specific flags where applicable

### 2. Load query and optional groundtruth

KNN search loads:

- query vectors
- KNN truthset if provided

Range search loads:

- query vectors
- range truthset if provided

### 3. Construct `PQFlashIndex<T>`

The constructor takes:

- aligned file reader
- `use_page_search`
- metric
- `use_sq` for KNN path only

The object then owns:

- in-memory PQ compressed base vectors
- disk-index metadata
- optional disk-PQ metadata
- medoid and centroid data
- optional partition metadata
- optional memory navigation graph
- optional cache-node data

### 4. Load the logical index

`PQFlashIndex::load()` uses:

- `index_prefix` to load sidecar files
- `disk_file_path` to open the actual disk layout

This split is important:

- the PQ tables and compressed vectors are always loaded from `index_prefix`
- the page-search or beam-search layout is chosen by `disk_file_path`

### 5. Load partition metadata if page search is enabled

If `use_page_search=1`, `load()` automatically loads:

- `<index_prefix>_partition.bin`

This creates:

- `gp_layout_`: page id to node layout
- `id2page_`: node id to page id

These two maps are what turn Starling search from node-level IO into page-level IO.

### 6. Load optional memory navigation graph

If `mem_L > 0`, search calls:

- `PQFlashIndex::load_mem_index()`

The memory index is a separate `diskann::Index<T, uint32_t>` used only for search-time seeding.

### 7. Load optional cache nodes

If `num_nodes_to_cache > 0`, KNN search generates a cache list from sample queries and then loads those nodes into:

- `coord_cache`
- `nhood_cache`

The cache list is generated by replaying sample queries through the active search path and counting visited nodes.

Range search currently uses a different cache path:

- it calls `cache_bfs_levels()` directly

## What `PQFlashIndex::load()` Actually Loads

`PQFlashIndex::load()` is the key runtime initialization stage.

It loads:

- main PQ pivots from `<index_prefix>_pq_pivots.bin`
- compressed base vectors from `<index_prefix>_pq_compressed.bin`
- disk index metadata from `disk_file_path`
- optional disk-PQ pivots from `<disk_file_path>_pq_pivots.bin`
- medoids from `<disk_file_path>_medoids.bin` when present
- centroids from `<disk_file_path>_centroids.bin` when present
- optional max-base-norm file for inner-product rescaling
- optional partition file if page search is enabled
- optional SQ max/min table if SQ is enabled

It also computes or derives:

- `data_dim`
- `aligned_dim`
- `disk_bytes_per_point`
- `max_node_len`
- `nnodes_per_sector`
- `max_degree`
- whether disk-PQ exists
- whether reorder data exists

## KNN Search Flow

## Entry point

- `tests/search_disk_index.cpp`

### Top-level runtime switch

For each `L` in the input `-L` list, KNN search chooses exactly one of:

1. `page_search_sq()`
2. `page_search()`
3. `cached_beam_search()`

The choice is controlled by:

- `use_page_search`
- `use_sq`

### Path A: Beam search

When:

```text
use_page_search = 0
use_sq = 0
```

search calls:

- `PQFlashIndex::cached_beam_search()`

This is the DiskANN-style baseline path.

#### Beam search behavior

- works on node-level graph expansion
- uses the in-memory PQ compressed base vectors for approximate distance screening
- reads node sectors from disk when expansion requires them
- can use memory-graph seeding if `mem_L > 0`
- can use cache nodes if `num_nodes_to_cache > 0`
- can optionally use reorder data if the index was built with appended full-precision payload

#### Beam search starting point

- if `mem_L > 0`, seed candidates come from the memory navigation graph
- otherwise search starts from the best medoid

### Path B: Page search

When:

```text
use_page_search = 1
use_sq = 0
```

search calls:

- `PQFlashIndex::page_search()`

This is Starling's main page-aware path.

#### Page search behavior

- candidates are still ranked using PQ distances
- physical IO is issued at page granularity using `id2page_`
- multiple nodes in the same page are evaluated together
- `page_visited` prevents repeatedly issuing IO for the same page
- `use_ratio` can limit how many vectors in a page are fully considered each time

#### Page search starting point

- if `mem_L > 0`, seed candidates come from the memory navigation graph
- otherwise search starts from the best medoid

### Path C: Page search with SQ

When:

```text
use_page_search = 1
use_sq = 1
```

search calls:

- `PQFlashIndex::page_search_sq()`

This follows the same page-level traversal logic as page search, but the disk payload is interpreted as scalar-quantized bytes and dequantized on the fly using:

- `frac`
- `mins`

loaded from:

- `<index_prefix>_sq_max_min.bin`

#### SQ limitations

- only supported for `float`
- rejected for beam search
- rejected for cache-node loading in the KNN CLI

## Memory Navigation Graph Seeding

If `mem_L > 0`, KNN and range search first query the in-memory navigation graph:

- `mem_index_->search_with_tags(...)`

The top `mem_L` tagged results are injected into the candidate set before disk traversal begins.

Practical meaning:

- `mem_L` is not a graph-build parameter at search time
- it controls the size of the memory-derived seed set
- larger values can improve disk-search entry quality at the cost of extra memory-side work

## Cache-Node Loading

KNN cache generation is performed by:

- `generate_cache_list_from_sample_queries()`

This method:

1. loads `<index_prefix>_sample_data.bin`
2. replays those queries through the currently selected search path
3. counts node visits
4. sorts nodes by visit count
5. keeps the top `num_nodes_to_cache`

Then `load_cache_list()` reads those nodes into memory, caching:

- coordinates
- adjacency lists

Beam search and page search both consult this cache at query time.

## Reorder Data During Search

If the index was built with disk-PQ plus appended reorder data, and the CLI passes:

- `--use_reorder_data`

then exact full-precision vectors stored in reorder sectors can be used for the final exact distance refinement of shortlisted candidates.

Restrictions:

- only valid for float data
- only meaningful if reorder payload exists in the built index

## Beamwidth Behavior

Search accepts:

- `-W` or `--beamwidth`

If `beamwidth > 0`, that value is used directly.

If `beamwidth == 0`, KNN and range search may tune beamwidth by calling:

- `optimize_beamwidth()`

The tuner evaluates candidate beamwidths on warmup queries and picks the one with best QPS subject to a latency constraint.

Beamwidth is capped by:

- `MAX_N_SECTOR_READS`

## `L` Search List Semantics

KNN and range search both accept one or more `L` values.

For KNN:

- each `L` is the candidate-list size for a full search run
- results are saved separately for each `L`

For iterative range search:

- `L` acts as the starting search width
- the code may double it repeatedly until stopping conditions are met

## Range Search Flow

## Entry point

- `tests/range_search_disk_index.cpp`

Range search has two major algorithms.

### Path A: Iterative KNN-to-range search

When:

```text
iter_knn_to_range_search = 1
```

search calls:

- `PQFlashIndex::range_search_iter_knn()`

This method repeatedly runs KNN-style search with increasing `L` until it believes enough points inside the radius have been found.

#### Behavior

- starts from `min_l_search`
- doubles `L` until a stop condition or `max_l_search`
- if `use_page_search=1`, uses `page_search()`
- if `use_page_search=0`, uses `cached_beam_search()`

This is the most general range-search path because it can operate with either page search or beam search.

### Path B: Custom page-based range search

When:

```text
iter_knn_to_range_search = 0
```

search calls:

- `PQFlashIndex::custom_range_search()`

This is a Starling-specific range-search path.

#### Hard requirements

- `mem_L > 0`
- `use_page_search = 1`
- `kicked_size > 0`

If those are not satisfied, the CLI exits with an error.

#### Behavior

1. Query the memory navigation graph for seeds within the target radius.
2. Optionally BFS inside the memory graph.
3. Convert seed nodes into page candidates.
4. Traverse disk pages round by round.
5. Add result points within the radius.
6. Expand only to new pages whose neighbors also appear promising.

This path is more specialized than iterative KNN search and depends on the memory graph to bootstrap the process.

### Path C: Iterative page search with persisted intermediate state

When:

```text
iter_knn_to_range_search = 1
kicked_size > 0
use_page_search = 1
```

the range binary may instead use:

- `custom_range_search_iter_page_search()`

This is a hybrid path that reuses intermediate page-search state across repeated expansions of `L`.

It uses:

- `PageSearchPersistData`
- a retained `ret_set`
- a retained `kicked` vector

to avoid restarting page search from scratch each round.

## Search Metrics And Output

## KNN output

For each `L`, KNN search writes:

- `<result_path>_<L>_idx_uint32.bin`
- `<result_path>_<L>_dists_float.bin`

The console summary reports:

- QPS
- mean latency
- P50 latency
- P99 latency
- P99.9 latency
- mean IOs
- CPU time
- RSS before memory index load
- RSS after cache load
- recall if groundtruth is present

## Range output

Range search primarily reports metrics to stdout:

- QPS
- mean latency
- P99.9 latency
- mean IOs
- CPU time
- recall if range groundtruth is present

The range path also computes:

- ratio of returned positives to true positives

as an additional diagnostic.

## Major KNN Parameters

- `--data_type`
  - `float`, `int8`, `uint8`
- `--dist_fn`
  - `l2`, `mips`, `cosine`
- `--index_path_prefix`
  - logical prefix for sidecar files
- `--disk_file_path`
  - physical disk layout to use
- `-K`
  - top-k to return
- `-L`
  - one or more search-list sizes
- `-W`
  - beamwidth; `0` means auto-tune
- `--search_io_limit`
  - maximum number of IOs per query
- `--mem_L`
  - number of memory-index seeds
- `--mem_index_path`
  - memory navigation graph path
- `--num_nodes_to_cache`
  - number of nodes cached in RAM
- `--use_page_search`
  - `1` for page search, `0` for beam search
- `--use_ratio`
  - fraction of a page evaluated each time
- `--use_reorder_data`
  - enable full-precision reorder payload if present
- `--use_sq`
  - enable SQ page search

## Major Range Parameters

- `--range_threshold`
  - target search radius
- `-L`
  - starting search-list size or sizes
- `-W`
  - beamwidth
- `--mem_L`
  - memory seed size
- `--mem_index_path`
  - memory graph path
- `--use_page_search`
  - switch between page search and beam-search-backed iterative KNN
- `--iter_knn_to_range_search`
  - `1` for iterative KNN-to-range
  - `0` for custom Starling range search
- `--kicked_size`
  - capacity of persisted kicked elements used in the interim page-search path
- `--custom_round_num`
  - number of rounds for custom range search; `0` means unbounded until natural stop
- `--use_ratio`
  - page evaluation fraction for page-search-based range methods

## Validation And Limit Rules

The CLI layer enforces several important constraints.

### KNN constraints

- `use_ratio` must be in `[0, 1]`
- `mips` requires `float`
- `use_sq` requires `float`
- `use_sq` requires `use_page_search=1`
- `use_reorder_data` requires `float`

### Range constraints

- `mips` requires `float`
- custom range search requires `mem_L > 0`
- custom range search requires `use_page_search = 1`
- custom range search requires `kicked_size > 0`

### Runtime constraints

- `beam_width` cannot exceed `MAX_N_SECTOR_READS`
- `mem_L > 0` requires a valid `mem_index_path`
- page search requires a valid partition file
- SQ requires a valid SQ max/min table

## How The Benchmark Script Chooses Search Modes

`scripts/run_benchmark.sh` uses:

- `USE_PAGE_SEARCH`
- `USE_SQ`
- `BM_LIST`
- `T_LIST`
- `CACHE`
- `MEM_L`
- `LS`
- range-specific variables

### KNN mode selection

- if `USE_PAGE_SEARCH=1`, the script requires `<prefix>_partition.bin` and uses `<prefix>_disk.index`
- if `USE_PAGE_SEARCH=0`, the script prefers `<prefix>_disk_beam_search.index`

### Range mode selection

The script forwards:

- `RS_ITER_KNN_TO_RANGE_SEARCH`
- `KICKED_SIZE`
- `RS_CUSTOM_ROUND`

to the range CLI.

## Practical Interpretation

If you only want to know which search mode to use:

1. Use beam search when you want the DiskANN-style baseline and do not need partition-aware IO.
2. Use page search when you want the Starling layout-aware path and already have `_partition.bin`.
3. Use memory seeding when you have a separately built memory navigation graph and want better disk entry points.
4. Use SQ only for float page search.
5. Use iterative KNN-to-range when you want the more general range-search path.
6. Use custom range search only when you deliberately want the Starling memory-seeded page-expansion method.
